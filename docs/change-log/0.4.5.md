# 0.4.5 (July 16, 2026)

`0.4.5` is a supportability and public-surface hardening release for the
`0.4.x` line. It does not try to expand the execution model. Instead, it makes
the current line easier to operate, easier to document, and easier to support
by formalizing machine-readable contracts around `agora doctor`, metrics,
acceptance, DLQ payload handling, install guidance, and plugin-family
documentation.

This release also refreshes the package story around the official first-party
plugin bundle so the boundary between `agora-etl` and `agora-etl-plugins`
stays explicit and operator-friendly.

## Highlights

- Added a shared `agora.core.doctor` contract surface with stable
  `CheckResult`, `DoctorReport`, `Status`, and
  `discover_doctor_readiness_providers()` primitives.
- Added new protocol-style supportability surfaces for machine-readable metrics
  and acceptance reporting so plugin/operator code can rely on stable runtime
  checks instead of ad hoc duck typing.
- Added `DLQPayloadPolicy` to centralize payload persistence behavior for raw,
  redacted, and encrypted dead-letter payloads.
- Added shared packaging/install helpers so CLI and runtime messaging can point
  operators to the correct `agora-etl-plugins[...]` extra consistently.
- Expanded the documentation set with canonical BigQuery and S3 family pages,
  a source-of-truth map, and a clearer official bundle story.
- Realigned root/core public exports, contract tests, and release verification
  so the shipped API and the tested API stay in sync.

## Core supportability contracts

### `agora doctor` is now a first-class contract surface

`agora doctor` was refactored to rely on reusable support primitives in
`agora.core.doctor` instead of keeping those semantics buried inside the CLI
implementation.

This release introduces:

- `DOCTOR_READINESS_ENTRYPOINT_GROUP = "agora.doctor.readiness"`
- `DoctorReadinessProvider` and `DoctorReadinessProviderEntry`
- structured `CheckResult` and aggregate `DoctorReport`
- stable `pass` / `warn` / `fail` status semantics
- machine-readable readiness aggregation grouped by backend

For plugin authors and operator tooling, this matters because readiness checks
can now be discovered and validated through an explicit public contract instead
of one-off implementation detail.

### Metrics and acceptance contracts were tightened

The observability surface now exposes explicit public protocols for:

- `MetricsSnapshotProvider`
- `PrometheusMetricsProvider`
- `AcceptanceReportProvider`

Helper predicates such as `has_metrics_snapshot()`,
`has_prometheus_metrics()`, and `has_acceptance_report()` make it easier for
CLI, health, release-gate, and plugin code to detect supported observability
surfaces safely.

### DLQ payload persistence is more explicit

`agora.core.dlq_policy.DLQPayloadPolicy` centralizes how dead-letter payloads
are stored:

- `raw()` keeps the payload unchanged
- `redacted()` masks common secrets and configurable fields/headers
- `encrypted()` stores a structured encrypted envelope with algorithm and key
  metadata

This gives downstream plugin and operator code a reusable contract for safe DLQ
storage instead of re-implementing redaction/encryption behavior per backend.

## Public API and packaging cleanup

### Root/core facades were rebalanced

The root `agora` facade and `agora.core` facade were refreshed so the public API
better reflects the intended boundary of the framework. Key related changes:

- new core exports now include `DLQPayloadPolicy` and the new observability and
  doctor support contracts
- root-level soft-deprecation guidance was clarified for legacy convenience
  exports that should move toward more specific `agora.core.*` imports over
  time
- frozen public-surface tests were updated so manifest drift is caught during CI

This is primarily a correctness and maintainability change: import paths become
more intentional, and release automation now has stronger guardrails against
accidental API drift.

### Packaging/install hints are now shared

The new `agora.core.packaging` helpers standardize install guidance for the
official plugin bundle:

- `distribution_requirement()`
- `first_party_plugin_requirement()`
- `pip_install_command()`
- `first_party_plugin_install_command()`
- `first_party_plugin_install_detail()`
- `first_party_plugin_family_from_module()`

These helpers are used to improve CLI/plugin-discovery output so operators get
clearer guidance such as `pip install 'agora-etl-plugins[redis]'` instead of
generic or inconsistent install hints.

### `agora plugins list` reports plugin provenance more clearly

The plugin-listing command now has better first-party package awareness and can
emit more useful metadata for discovered items, including:

- entry-point group and registry metadata
- compatibility/manifest status where available
- first-party family install hints based on module namespace
- clearer distinction between built-in, first-party plugin, and third-party
  surfaces

## Documentation and package-boundary refresh

This release substantially improves the public docs around the official plugin
ecosystem.

### New family landing pages

Two backend families now have dedicated public pages:

- `docs/plugins/bigquery.md`
- `docs/plugins/s3.md`

These pages document:

- support label and maturity boundary
- install extras
- public entrypoints
- recovery/resume boundary
- operational hooks
- required validation gate for public support claims

### Better source-of-truth mapping

The new `docs/source-of-truth.md` page defines which document is authoritative
for package boundary, runtime guarantees, plugin maturity, CLI behavior, and
support claims. This helps keep README summaries from drifting away from the
canonical docs set.

### Official bundle story is clearer

`docs/plugins/index.md` and `docs/plugins/official-bundle.md` now describe the
`agora-etl` / `agora-etl-plugins` split more explicitly:

- core owns runtime semantics and stable framework contracts
- plugins own backend-specific integrations and validation matrices
- BigQuery and S3 are documented as production-ready dataset backends with
  bounded scope
- advanced composed helpers are intentionally not positioned as first-stop
  onboarding primitives

## Testing and release verification

This release adds or expands tests around:

- doctor readiness provider contracts
- acceptance-report provider contracts
- metrics snapshot / Prometheus provider protocols
- DLQ payload policy behavior
- packaging helper output
- root/core public export manifests
- CLI output and supportability paths

The result is a more trustworthy release gate for `0.4.x`: the repository
checks both behavioral correctness and public-surface consistency rather than
only implementation detail.

## Upgrade notes

- No config migration is required.
- This is intended as a non-breaking patch release within the existing `0.4.x`
  line.
- Teams with custom doctor readiness integrations should align them to the new
  `agora.doctor.readiness` provider contract.
- Teams with custom DLQ persistence logic may want to adopt `DLQPayloadPolicy`
  to standardize redaction and encryption behavior.
